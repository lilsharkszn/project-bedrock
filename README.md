# Project Bedrock — Retail Store EKS Microservices Capstone

A production-style Cloud DevOps capstone: a resilient microservices retail store deployed to AWS EKS and supporting AWS services, fully provisioned with Terraform and deployed via Helm. Includes observability, serverless asset processing, and a GitHub Actions CI/CD pipeline that plans on PRs and applies on merges.

Last updated: 2026-06-19 | Project: karatu-2025-capstone | Student ID: alt-soe-025-4423

---

## At a glance
- Infrastructure: VPC (2 AZs), Amazon EKS (v1.34), RDS MySQL (catalog), RDS PostgreSQL (orders), DynamoDB (carts), S3 (state + assets), IAM, ALB (Ingress), cert-manager (Let's Encrypt), CloudWatch/FluentBit, Lambda (S3-triggered asset processor).
- Application: retail-store-sample-app (UI, catalog, cart, orders, checkout).
- Provisioning: Terraform (>= 1.5.0).
- CI/CD: GitHub Actions (.github/workflows/CI_CD.yml) — plan on PR, apply on merge.
- Region used in examples: us-east-1.

Architecture diagram: `architecture-diagram.png` (top-level)

How it fits together:
1. Terraform provisions core AWS resources (VPC, EKS, RDS, DynamoDB, S3 buckets, IAM roles/policies, CloudWatch).
2. After EKS nodes are ready, Terraform/Helm installs the retail-store-sample-app into the `retail-app` namespace, configures ALB Ingress, cert-manager, and observability agents.
3. CI posts plan output on PRs and runs apply on merges; the apply step generates a redacted `grading.json` and commits it back.

## Deploy to AWS (recommended flow)
From a workstation with AWS credentials set (or via GitHub Actions):

1. Clone:
```
git clone https://github.com/lilsharkszn/project-bedrock.git
cd project-bedrock/terraform
```

2. Initialize Terraform:
```
terraform init
```

3. Option A — Full apply (single step):
```
terraform apply -auto-approve
```

3. Option B — Staged apply (what `infra-up.sh` automates — safer when first provisioning):
- The repo contains `infra-up.sh`, which:
  - Runs a first targeted apply for core infra (VPC, EKS, RDS, DynamoDB, IAM pieces).
  - Configures `kubectl` and EKS access entries.
  - Waits for nodes to be Ready.
  - Runs a second pass `terraform apply` to install Kubernetes/Helm resources.
To run:
```
chmod +x infra-up.sh
./infra-up.sh
```

4. After apply, update kubeconfig locally:
```
aws eks update-kubeconfig --name project-bedrock-cluster --region us-east-1
kubectl get pods -n retail-app
kubectl get ingress -n retail-app
```

5. The CI workflow generates `grading.json` from `terraform output -json`, redacts credentials and commits it back when running in GitHub Actions. Locally you can inspect:
```
terraform output -json > grading.json
```

## CI/CD (what happens in this repo)
Workflow: `.github/workflows/CI_CD.yml`

- On pull_request: runs `terraform init`, `terraform validate`, `terraform plan`. The plan output is posted as a comment on the PR (truncated if > 65k chars). The step intentionally fails the job if the plan exit code is non-zero.
- On push to `main` or manual dispatch: installs `kubectl`, configures kubeconfig for the EKS cluster, runs `terraform apply -auto-approve`, generates a redacted `grading.json`, commits it back to the repository, and uploads `grading.json` as an artifact.

Important: The workflow expects the GitHub repository secrets:
- `AWS_ACCESS_KEY_ID`
- `AWS_SECRET_ACCESS_KEY`

If you prefer not to have `grading.json` committed back, modify the `Terraform Apply` job to upload it only as an artifact and skip the commit step.

## TLS / HTTPS notes
- cert-manager and a ClusterIssuer for Let's Encrypt are configured in the Terraform manifests (HTTP-01 challenge path). The project used a dynamic DNS provider (NoIP) — some providers restrict record types needed for certain ACME flows.
- Recommendation: For fully automated HTTPS in production or CI:
  - Use DNS-01 challenges via a DNS provider that supports API updates (Route 53, Cloudflare, etc.). DNS-01 avoids constraints of HTTP challenge and CNAME requirements.
  - If using Route 53, configure IAM credentials that Terraform / cert-manager can use to create the TXT records (or use cert-manager DNS provider integration).

## Post-deploy verification & common troubleshooting
- Verify pods:
```
kubectl get pods -n retail-app
```
- Inspect EKS cluster:
```
aws eks describe-cluster --name project-bedrock-cluster --query 'cluster.{Name:name,Version:version,Status:status}' --output table
```
- Check Lambda logs:
```
aws logs tail /aws/lambda/bedrock-asset-processor --since 5m
```
- HTTP check:
```
curl -s -o /dev/null -w "%{http_code}" http://<app-ddns-or-alb-hostname>
```

Common issues and fixes:
- Pods pending: `kubectl describe pod <name> -n retail-app`
- DB connection fails: ensure RDS security group permits connections from EKS node security group
- Ingress has no ADDRESS: check AWS ALB Controller logs in `kube-system` namespace and ensure ALB controller IAM policy/role are attached
- carts CrashLoopBackOff: verify DynamoDB table exists and GSI `idx_global_customerId` is present
- Unauthorized kubectl calls in CI: ensure workflow configures kubeconfig and that IAM access has been associated for the admin user
- Terraform state lock stuck: `terraform force-unlock <LOCK_ID>`
